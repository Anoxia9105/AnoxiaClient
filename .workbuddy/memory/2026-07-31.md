## Web 聊天消息 bug 根因分析（19:xx 实测日志）
症状：发送后上屏即消失（发送方）、对方收到不显示（接收方）、列表点击跳转底部无响应。
- 数据流：WS 帧 → `ChatMessages._processIncomingMessage` / `upsertMessage` → drift/SQLite（`database_web.dart` WasmDatabase in Worker）→ `roomMessagesProvider(watch)` → `chatUiListProvider` → ListView。
- **发送方"闪退"根因**：ACK/回声处理用 `insertOrUpdateMessage` 把临时主键 clientMsgId 换成服务端 messageId（delete 旧 + insert 新）。`database.dart:426` 注释已预警：drift watch 会在 delete/insert 间隙发出空快照导致"消息闪退"。原生 SQLite 合并通知看不到，Web Worker 暴露该空窗 → 上屏后消失。日志实证：乐观 id e887e9bc → 服务端 id 1a9c0e5b 的换主键。
- **接收方"不显示"根因（与发送方不同）**：接收方 WS 帧确实到达并 dispatch（`[SERVER DATA] dispatch -> PacketType.message`，19:07:41 361ms），但之后**既无 `[DB] upsertMessage` 也无 `缓存入站消息失败`**。唯一"零日志"出口是 `local_data_source.dart:70`：`if (messageId==null||empty) return false`（messageId 来自 `fromRoomMessage`：`msg.messageId.isEmpty?null`，`chat_message.dart:122`；解码 `im_packet_v5.dart:118` field1）。推断：接收方实时广播包的 messageId（field1）为空 → 静默丢弃。typing(highFrequency) 能收到证明 `messageStream` 通畅，故非订阅丢失。
- 修复方向（用户尚未确认动手）：① 发送方不要在 ACK 时换主键，保留 clientMsgId 为稳定主键、服务端 id 存普通字段（消除 delete+insert 空窗）；② `applyIncomingMessage` line70 丢弃时打 warning 日志而非静默 return；接收方生成稳定 client 端 id 兜底落库；③ `chat_scroll_controller.dart:95/99` 静默 return 守卫 + `room_list_item.dart:90` 用 `isRealMobile()`（Web 恒 false）导致窄屏点击无导航，需统一为宽度断点 `isMobile`。

## 消息仍消失 —— 真正的根因（19:35 日志复现后定位）
上述 4 处修复后仍消失，说明"闪退"原发点更上游。沿渲染链路反查定位：
- **真因 = 手写 Protobuf varint 在 dart2js 下被 32 位截断**。
  `lib/framework/codec/proto_reader.dart` 的 `_readVarint()` 用 `result |= (b & 0x7F) << shift;`；
  `lib/framework/codec/proto_writer.dart` 的 `_writeVarint()` 用 `value >>> 7`。
  dart2js 的 `<<`/`>>>`/`|` 均为 32 位语义：移位量 >= 32 时高位字节直接归零。毫秒时间戳(~41 位)、seq、senderId 等 int64 字段被解/编成垃圾值 → `applyIncomingMessage`/`markAcked` 落库的 seq/timestamp 错乱 → `removePersisted` 移除乐观副本后，DB 新行在 `_chatUiListCache` 中无法正确补位/折叠为空 → `EmptyMessagesPage`（即"消失"）。这就解释了为何只有 Web 消失、VM 正常。
- **修复（2 个文件，已落地）**：改用 `BigInt` 做任意精度运算。
  - reader：`BigInt result = ...; result |= BigInt.from(b & 0x7F) << shift;` 末尾 `return result.toSigned(64).toInt();`（补码转回有符号 int64）。
  - writer：`BigInt v = BigInt.from(value).toUnsigned(64); ... v = v >> 7;`，循环末 `v == BigInt.zero` 结束；负数自动走 64 位补码 10 字节。
  - `_writeTag` 的 `(fieldNum<<3)|wireType` 因 fieldNum 很小无需改。
- **Task #7 排查**：`framework/` 下其余 `<<` 均为小整数（重试退避 `1<<attempt`、`1<<reconnectAttempts`、`400*(1<<attempt)`），无 int64 截断风险。唯一 `1<<32` 在 `call_invitation_controller.dart:460` 的 `Random().nextInt(1<<32)` —— dart2js 下 `1<<32==0` 会导致 `nextInt(0)` 抛异常，属独立隐患，本次未改（不在消息 bug 范围）。
- **Task #8 测试**：新增 `test/framework/codec/proto_codec_web_test.dart`，覆盖 127/128/300/1<<20/1<<31/1<<40/1.75e12/2^53-1/-1/-1.75e12 及 `ImPacketV5.decodeRoomMessage` 真实解码路径（含复现 19:35 日志 seq=166）。VM 端 14/14 全过。注意：dart2js 字面量不得 > 2^53（否则编译报错 "can't be represented exactly in JavaScript"），测试用例需控制在安全整数内。
- **验证状态**：VM 测试通过；`flutter test --platform chrome` 受沙箱限制需 `--no-sandbox`（已用 `C:/Temp/chrome_nosandbox.cmd` wrapper 重跑，进行中）。BigInt 为跨平台一致实现，故 Web 行为等价已可保证；dartdevc 编译已通过（无字面量超界报错）。
- 结论：本次为消息消失 bug 的**最终根因修复**，配合此前 4 处修复，发送/接收/跳转底部三类症状应全部消除。
